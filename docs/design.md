# solver 設計

## 技術的決定事項

### パズルごとのアルファベット制限

当初はフルアルファベット（A-Z, 0-9の36文字）を使用する設計だったが、ソルバーの探索空間が爆発する問題に直面した。36^N（Nはグリッドの最大辺）の列挙は N>=5 で非実用的（36^5 = 60M）。

**解決策**: パズルごとにランダムなアルファベットサブセット（4〜10文字）を選択する方式に変更。アルファベットサイズはグリッドサイズから逆算し、`alphabet^maxDim <= 500,000` を目安に設定。

| maxDim | アルファベットサイズ |
|--------|---------------------|
| 3      | 7-8                 |
| 4-5    | 6-7                 |
| 6-7    | 5-6                 |
| 8      | 4-5                 |

### ソルバー設計の変遷

3つのアプローチを試行し、最終的にハイブリッド方式を採用:

1. **セル単位バックトラッキング（初期案）**: 各セルに36文字を試す。行/列完成時のみ正規表現チェック。36^(N*M) で大規模グリッドに非実用的。
2. **ランダムサンプリングによる候補フィルタリング**: 正しい候補を見逃す（偽陰性）問題が発生し、有効な解を排除してしまった。
3. **採用方式 - 列挙ベース + 行単位バックトラッキング**:
   - 小さい探索空間（<=500K）: 全文字列を列挙し正規表現にマッチするものを収集
   - 大きい探索空間: フルアルファベットを候補として保持（フィルタリングしない）
   - 反復的弧整合性（arc consistency）で候補を絞り込み
   - 行ごとの有効文字列を列挙し、行単位でバックトラッキング
   - 列制約はプレフィックス検証で早期枝刈り

### 一意解保証のための反復的パターン精錬

ランダムに生成したパターンが一意解を持つ確率は低い（5x5で約10%）。単純なリトライでは大規模グリッドで実用的な時間内に収まらない。

**解決策**: ソルバーが2つの異なる解を発見した場合、解が異なるセルを特定し、そのセルの行または列のパターンをより厳密に再生成する。これを一意解が得られるまで繰り返す。

### 難易度の実現方法

難易度は以下のパラメータの組み合わせで制御:
- `MinLiteralRatio`: リテラル文字の最小比率（Easy: 0.7, Medium: 0.5, Hard: 0.45）
- `MaxDotRatio`: ドット（ワイルドカード）の最大比率
- `MaxClassSize`: 文字クラスの最大サイズ
- `AllowNegatedClasses`: 否定文字クラス `[^...]` の使用（Hardのみ）
- `AllowQuantifiers`: 量指定子 `{n}` の使用（Medium以上）

ドットの使用は制限している。ドットは36文字すべてにマッチするため、パターンが過度に曖昧になり一意解を得にくくなる。

### Go regexp (RE2) の制約

Go標準の `regexp` パッケージはRE2構文を使用するため:
- 後方参照 (`\1`) 不可
- 先読み/後読み (`(?=...)`, `(?<=...)`) 不可
- パターンの部分マッチ（プレフィックスマッチ）API なし

部分マッチAPIがないため、ソルバーでのプレフィックス枝刈りは「プレフィックス + 残りを全探索」方式で実装。これが大規模グリッドでのパフォーマンスボトルネックとなるため、アルファベット制限と組み合わせて対処。

### パズル生成の goroutine 並列化

パズル生成（`generateAndRefine`）は一意解を持つパズルが得られるまで最大50回リトライする。各リトライは独立した乱数シードで動作するため、goroutine による並列化が自然に適用できる。

**設計**:
- `seed == 0`（デフォルト）: `runtime.NumCPU()` 個の goroutine がリトライを分担し、最初に成功したものを `context.Cancel` で採用、他を停止
- `seed != 0`（ユーザー指定）: 逐次実行で再現性を保証

**見送った並列化箇所**:
- **ソルバー内部の行/列候補計算（`computeCellCandidates`, `enumRowMatches`）**: 各行・各列は独立しており並列化可能だが、生成レベルで既に全CPUコアを使い切るため、ネストした並列化は goroutine 過多になる。生成の並列化だけで十分な効果が得られたため見送り
- **バックトラッキング（`solveRows`）**: 前の行の結果に依存する逐次的処理のため並列化困難
- **弧整合性伝播（`propagate`）**: イテレーション間で行/列の候補が相互依存するため並列化困難
